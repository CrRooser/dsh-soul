# dsh-soul 设计说明

这份文档记录 v0.1 的取舍。想要「为什么」而不是「怎么做」的话，看这里。

---

## 1. 问题定义

新会话从零开始。模型不记得上次聊了什么、你是谁、事情做到哪一步。

DSH 里不存在权重继承——唯一能做的，是在新会话开始时把一段文本摆进上下文。所以：

> **记忆质量的上限 = 那段文本的质量，不是存储量。**

这个判断决定了后面所有的设计：重点不在「怎么存得多」，而在「怎么保证注入的那一千多字始终干净」。

## 2. 为什么不用向量检索

v0.1 用关键词 + 权重打分，理由：

- 卡片规模在几百张，全量扫描的成本可以忽略
- 中文用二元组滑窗召回，对短查询的效果比想象中好
- 没有索引就没有索引维护、没有维度漂移、没有「改了模型得重建」

什么时候该换：卡片过两千张，或者实测召回率明显不够。到那时再加，而不是一开始就背着。

## 3. token 预算

### 3.1 三种方案的账

设每轮注入 400 token，会话 N 轮，注入内容留在历史里（在 DSH 里它确实会留下）：

| 方案 | N=10 | N=50 | N=200 |
|---|---|---|---|
| A 每轮注入 | 2.2 万 | 51 万 | 804 万 |
| B 首轮冻结画像 | 0.38 万 | 1.14 万 | 3.99 万 |

B 的算法：首轮 1900 token，之后每轮重发同一段前缀，按缓存命中价（十分之一量级）折算 ≈ 190/t轮。

B/A 在 N=50 时约 1/45，N=200 时约 1/200。差距这么大的根本原因是 **A 每轮都在变动处打断缓存**，而 B 的前缀从第一次请求起就逐字节不变。

### 3.2 因此产生的三条硬约束

1. **画像在会话开始时冻结。** 会话中修改只写卡片，下个会话生效。
2. **注入块内不得出现时间戳、计数器、随机数。** 任何一次字节变动都会让缓存从该处失效。
3. **画像总量恒定。** 四段各有上限，总预算 1400 字。

第 1 条同时还解决了一个非技术问题：人格不该在对话中途变脸。

## 4. 数据结构

### 卡片

```jsonc
{
  "id": "c_1a2b3c4d",
  "kind": "fact",            // fact | user | trait | rule
  "text": "部署脚本放在 scripts/deploy.ps1",
  "tags": ["部署"],
  "scope": "project:d:/proj-a",   // 或 "global"
  "confidence": 0.9,
  "weight": 1.4,             // 被确认/合并的次数
  "hits": 3,
  "createdAt": 0, "updatedAt": 0, "lastHitAt": 0,
  "evidence": [{ "sessionId": "s_xxx", "at": 0 }],
  "supersededBy": null,
  "status": "active"
}
```

四种 `kind` 的区别是有意的：

- `fact` 关于项目或世界
- `user` 关于用户本人
- `trait` 我自己表现出的倾向
- `rule` 我给自己定的做法

`trait` 单独一类，是为了将来能对它施加更严的升级门槛（见第 6 节）。混在 `fact` 里，就没法区分「观察到的事实」和「对自己的判断」。

### 作用域

`scope` 让项目记忆按工作目录隔离，`global` 的记忆（人格、关系）全局共享。换项目不会串味——这是 meow-memory 这类「按 workspace 存一个大库」的做法容易出问题的地方。

### 画像

```jsonc
{
  "version": 1,
  "updatedAt": 0,
  "sections": { "who": "", "context": "", "conduct": "", "rapport": "" }
}
```

渲染时按 `who → context → conduct → rapport` 的顺序分配预算，超了就从后往前截断。顺序即优先级。

### 「最近确认」短带

严格按「读入只走画像」的原则，卡片是不该被注入的。但 v0.1 没有凝结机制，画像不会自己更新——结果就是：写进去的事实，新会话里看不见。

这在集成测试里直接暴露了（`首轮注入记忆块` 一条一开始就是红的）。

补丁是有界的：注入块里加一段「最近确认」，只放最近动过的 6 张卡、合计不超过 260 字。它是短期工作记忆，不是第二个画像——条数和字数都封死，不会随会话变长而膨胀。

真正的解法仍然是 P1 的凝结：卡片蒸馏进画像，短带自然变薄。

## 5. 生命周期

| 时机 | 钩子 | 行为 |
|---|---|---|
| 每轮开始 | `agent/pre-step` | 每个会话**只在第一次**注入；压缩后解除标记以便重注入 |
| 用户发消息 | `session/event` `user/message` | 记录最近几句话，供下次交接 |
| 压缩结束 | `session/event` `compaction/end` | 解除注入标记 |
| 会话销毁 | `agent/disposed` | 清理标记、落盘 |

注入方式是构造一条 `role: "user"` 的消息，插在**最后一条真实用户消息之前**——离问题最近的位置，注意力最好。

fail-open 贯穿全部路径：注入失败就放行原始消息，写入失败就不写。记忆坏了绝不能挡住对话。

## 6. 「养成」的规则（P1 实现）

这一节是设计意图，v0.1 尚未实现。

### trait 的升级门槛

一条 `trait` 卡片要升进画像，必须满足：

- 跨 **≥2 个会话**
- 出现 **≥3 次**（权重累加）
- 至少有一次「这样做有效 / 用户认可」的证据

不够格的一律留在卡片层。这条门禁防的是最坏的情况：**一次性的迎合被固化成性格**。

### 反自证循环

画像里每条 trait 带「最后被验证时间」，60 天没再被验证就降级回卡片。

否则会出现：「我因为写过所以我是」。一个人格只靠自己的注脚活着，是这类系统最典型的退化方式。

### 凝结（dream）

每 20 张新卡或每 7 天跑一次：

1. 合并重复、衰减权重、淘汰矛盾项
2. 重写画像那一段
3. 保存旧版本，可回滚、可比 diff

**只在错峰窗口跑**（北京时间 00:30–08:30），高峰期排队而不是跳过——「检测到高峰就放弃这一轮」是 meow-memory 的一个明显缺陷，会永久丢掉那批记忆。

## 7. 未做的事（以及为什么）

| 没做 | 原因 |
|---|---|
| 向量检索 | 见第 2 节 |
| LLM 自动抽取 | 放 P1。v0.1 先证明「存储 + 注入」这条主干是通的 |
| Schemastery 的 Config 导出 | 会引入一个运行时外部依赖；宁可暂时没有设置页表单，也不能让插件因为解析不到包而整体加载失败 |
| 物理删除 | 只做「退役」。删掉之后模型容易重新推断回来，留着反而能阻止重复犯错 |
| `/soul` 命令 | 放 P1。v0.1 用工具就能完成全部操作 |

## 8. 风险

- **画像漂移**：靠「证据门槛 + 到期降级」压住，压不到零
- **中文分词召回率**：二元组的极限就在那里，接受
- **首轮 1900 token**：如果每次都开新会话、每个会话只有两三句，这个方案不划算——那种用法下把 `profileBudget` 调小是唯一正解
- **和 meow-memory 并存**：两边都注入就重复了。要同时用必须明确分工
